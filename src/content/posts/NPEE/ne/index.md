## 物理层

### 通信基础

单向通信、半双工通信、全双工通信。

速率、波特、比特与带宽。

码元传输速率单位为波特，一波特可以携带 n 位比特的信息量。

#### 奈奎斯特定理

公式：

$C_{max} = 2B \log_2(V) \quad (\text{bps})$

物理意义：信道在理想无噪声状态下，码元传输速率的极限是 $2B \text{ Baud}$（$B$ 为信道带宽，单位 $\text{Hz}$）。如果一个码元携带 $\log_2(V)$ 个比特信息（$V$ 为离散电平数或码元状态数），则最大信息传输速率为 $2B \log_2(V)$。

适用场景：题目明确提到了“无噪声信道”，或者给出了“调制电平数/状态数 $V$”且要求极限速率。

#### 香浓定理

公式：

$C_{max} = B \log_2(1 + \frac{S}{N}) \quad (\text{bps})$

物理意义：在存在随机热噪声的信道中，即使码元状态数无限多，受噪声干扰影响，信息的传输速率依然存在绝对极限。其中 $S/N$ 为信噪比（必须是无量纲的功率比值）。

注意换算：若题目给的是分贝值（$\text{dB}$），需用公式换算：

$\text{信噪比}(\text{dB}) = 10 \log_{10}(\frac{S}{N}) \implies \frac{S}{N} = 10^{(\text{dB} / 10)}$
注：如果题目涉及信号与噪声的幅度比，功率比就是幅度比的平方；若要开方求幅度，也必须写成 $(\dots)^{1/2}$ 的形式。

#### 通信基础相关的计算辨析

1. 如果机械的限死频率，那么只需要看有没有达到上限，如果没有的话，那么就直接按这个频率算，不需要管其他的参数
2. 需要注意题目是不是要求算极限，如果不是极限，那么按照正常的公式计算即可
3. 对于没有提到的信息，不要多考虑，例如本题完全没给计算奈奎斯特定理的条件，仅给了香浓定理的条件，那么久不需要考虑奈奎斯特定理

双重约束取最小：若题目既给了带宽和调制进制，又给了信噪比，且问“信道的最大极限速率”，此时两个定理都要算一遍，取两者的最小值作为最终的物理极限速率：

$C_{real\_max} = \min\big(2B \log_2(V),\; B \log_2(1 + S/N)\big)$

> 上述的 B 其实就是 W，是一个东西。

极限情况下（奈奎斯特定理）：$\text{极限数据率 } C_{max} = \underbrace{2W}_{\text{极限波特率 } R_B} \times \underbrace{\log_2(V)}_{\text{每个码元的比特数}} \quad (\text{bps})$

非极限情况下，事实上就是：$S = R_B \times \log_2(V) \quad (\text{bps})$

而在香浓公式里面，则没有波特率存在。

```text
时刻               H3 (主动关闭方)                        S (被动关闭方)
───               ──────────────                        ─────────────
t               [ESTABLISHED]                          [ESTABLISHED]
                  │
                  ├─ 发送 FIN=1 ─────────────────────────> (在途中，耗时 0.5 RTT)

                [FIN_WAIT_1]
                  │
t + 0.5 RTT       │                                      │ (收到 FIN，状态变为 CLOSE_WAIT)

                  │                                      │  立刻合并不单发 ACK，而是直接
                  │                                      │  连同自己的 FIN+ACK 一起回传！
                  │ <──────────────── 发送 FIN=1, ACK=1 ─┤ (或者分开连着发，耗时 0.5 RTT)

t + 1.0 RTT       ├─ 收到 S 的 FIN，发送最终 ACK ────────> (在途中，耗时 0.5 RTT)
```

### dns

常用于 53 端口，采用 UDP。

#### 域名服务器层级

基于 blog.attilio.cc 为例。

- . 为根域名服务器，一般省略
- .cc 为顶级域名服务器
- .attilio.cc 为权限域名服务器

可能设置多个权限域名服务器，例如在这里也可以把 blog 也设置为权限域名服务器。

一般做最坏例的讨论。

#### 迭代查询

如果前面有 `www`，忽略之，目标域名为 `blog.attilio.cc`。

首先考虑**单权限域名服务器**的情况（假设整个二级域及其子域都统一由一台权限域名服务器管理，不进行子域委派）：

本机向本地域名服务器发起**递归查询**，委托其代为打听；本地域名服务器在本地无缓存的情况下，对外进行**迭代查询**：

1. 本地域名服务器向根域名服务器发送请求，根域名服务器收到请求后，发现这是 `.cc` 结尾的域名，返回 **`.cc` 顶级域名服务器** 的 IP 地址；
2. 本地域名服务器向 `.cc` 顶级域名服务器发送请求，`.cc` 顶级域名服务器收到请求后，发现这是 `attilio.cc` 的域，返回 **`attilio.cc` 权限域名服务器** 的 IP 地址；
3. 本地域名服务器向 `attilio.cc` 权限域名服务器发送请求，`attilio.cc` 权限域名服务器收到请求后，由于没有单独设立下一级子域服务器，它直接在内部记录中查到了 `blog` 的主机映射，**直接返回 `blog.attilio.cc` 对应的最终 IP 地址**。

本地域名服务器对外进行了 3 次迭代查询；

本机自身只向本地域名服务器发送了 1 次查询请求；

整个解析流程在网络上一共产生了 4 个查询报文（本机 1 次 + 本地 DNS 3 次），最终成功得到 `blog.attilio.cc` 的 IP 地址。

然而，如果是最坏情况，也就是存在子域委派，那么就需要进行更多的查询。

修改 3，本地域名服务器向 `attilio.cc` 权限域名服务器发送请求，`attilio.cc` 权限域名服务器收到请求后，发现 `blog` 是子域，所以委派给 `blog` 权限域名服务器，返回 `blog` 权限域名服务器的 IP 地址；

增加 4，本地域名服务器向 `blog` 权限域名服务器发送请求，`blog` 权限域名服务器收到请求后，查询到 `blog.attilio.cc` 的 IP 地址，返回。

综上，要辨析清楚返回的是 DNS 服务器的 IP 地址还是对应解析的 IP 地址。

#### 递归查询

对于递归查询和上述类似的，只不过变成老大亲自去跑腿，本地域名服务器只需要发一次即可。

不过需要注意的是，递归查询和迭代查询是可以随时替换的，例如整条链路可能一部分是递归，一部分是迭代，不一定是课本标准模型里那样。

比如说，顶级域名服务器采用递归查询，而权限域名服务器使用迭代查询等。

### ftp

名称：文件传输协议（File Transfer Protocol），基于 TCP 的客户端/服务器（C/S）模型。
核心特征：带外（Out-of-band）控制，即控制信息和实际数据分别在两条不同的 TCP 连接中传输。

#### 两个端口与两条连接

控制连接（端口 21）：
用于传输客户端的用户名、密码、各种操作命令（如 PUT、GET、LS）以及服务器的应答状态码。
生命周期：在整个 FTP 会话期间一直保持打开状态，直到用户退出登录。

数据连接（端口 20 或随机高位端口）：
用于实际传输文件内容、目录列表等数据。
生命周期：每次有数据传输需求时才临时建立，传输完毕后立即关闭。

#### 两种工作模式（谁连谁、用不用 20 端口的本质区别）

主动模式（PORT 模式，服务器主动找客户端）：
控制连接：客户端随机选择端口 N，连接服务器的 21 端口。
客户端通知：客户端在本地监听端口 N+1，并通过控制连接向服务器发送 PORT 命令，告知服务器：“我的 IP 和端口是 N+1”。
数据连接：服务器使用固定的 20 端口，主动向客户端的 N+1 端口发起 TCP 连接。
缺陷：若客户端处于内网或开启了防火墙，服务器主动发起的连接会被客户端防火墙拦截。

被动模式（PASV 模式，客户端主动找服务器，现代主流）：
控制连接：客户端连接服务器 21 端口后，向服务器发送 PASV 命令。
服务器响应：服务器在本地开放一个临时的随机高位端口 P，并告知客户端。
数据连接：客户端主动向服务器的端口 P 发起 TCP 连接。
注意：在被动模式下，服务器的数据传输根本不用 20 端口，而是使用随机高位端口。

### stmp

#### stmp 解析

定位：纯文本的、基于推（Push）模式的邮件传输协议。
端口：默认明文端口 25，加密端口（SMTPS）常用 465 或 587。
机制与缺陷：
工作在 TCP 之上，客户端或源邮件服务器将邮件主动“推”送到目的邮件服务器。
致命缺陷是最初只支持传输 7 位 ASCII 码文本，不能直接传输可执行文件、图片、音频及非 ASCII 编码的文字（如汉字）。

#### pop3

定位：基于拉（Pull）模式的邮件读取协议。
端口：默认端口 110，SSL 加密端口 995。
机制：用户代理连接到邮件服务器，将邮件下载到本地计算机阅读。
工作模式：
删除模式：从服务器拉取邮件后，立刻在服务器端删除该邮件。
保留模式：拉取到本地后，服务器端依然保留副本。缺点是不同设备间不能很好地同步已读/未读状态（后被支持双向同步的 IMAP4 取代）。

#### mime

定位：不是独立的传输协议，而是寄生在 SMTP 之上的内容格式扩展标准。
机制：在原有邮件首部增加了额外字段（如 MIME-Version、Content-Type、Content-Transfer-Encoding）。
作用：将非 ASCII 码的二进制数据（如图片、视频、附件、汉字）通过 Base64 或 Quoted-Printable 等编码规则，全部无损转换成普通的 7 位 ASCII 码文本，使得老旧的 SMTP 能够安全可靠地传输富文本和多媒体内容。接收端再根据 MIME 首部反向解码还原。

#### http 邮件

机制：现代主流模式（如 QQ 邮箱、Gmail 网页版）。
流向与协议分工：
PC 端浏览器到源邮件服务器：使用 HTTP/HTTPS 协议（包含发送邮件和读取邮件）。
两个不同邮件服务器之间互转：依然使用传统的 SMTP 协议通过互联网中继转发。
目的邮件服务器到接收方浏览器：接收方同样使用 HTTP/HTTPS 协议登录网页拉取并阅读邮件。
优势：客户端无需安装专门的邮件客户端（如 Outlook），无需配置繁琐的 SMTP/POP3 端口，有浏览器即可收发。

### http

http 常用端口为 80，https 常用端口为 443。

考虑这样一个场景：内网 1 中的主机 A 需要向内网 2 中的 Web 服务器主机 B 发送一个 HTTP 请求。主机 A 首先从本地随机分配一个源端口，以源套接字 192.168.x.x:11452 发送数据报，目的地址设置为内网 2 网关的公网 IP 及对应服务端口，例如 211.211.211.211:80。

当数据报到达内网 1 的默认网关（NAT 路由器）时，网关将其源私网 IP 和端口转换为内网 1 自身的公网 IP 和新分配的端口，并记录到 NAT 转换表中，然后将该报文转发至公网。

公网路由将报文送达内网 2 的默认网关路由器（具有公网 IP 211.211.211.211）。该路由器通过预先配置的端口映射规则（如将外网 80 端口映射到内网主机 B 的 80 端口），将目的 IP 和端口转换为内网主机 B 的私网套接字，最终将 HTTP 请求准确投递给内网 2 中的主机 B。

#### 四种 http 形式

以发送 index.html（包含 5 个图像为例）

1. 非持续连接（无并行 / 串行）
机制：每个对象的获取都必须新建一次 TCP 连接，且传输完毕后立刻断开该连接。
过程：
获取 html 消耗 2 RTT（三次握手 1 RTT + 请求与返回 1 RTT）；
后续 5 个图像每个依次单独建连并获取，各消耗 2 RTT。
总耗时：2 + 5 * 2 = 12 RTT。

2. 非持续连接（带并行 / 并发）
机制：浏览器允许同时建立多个并行的 TCP 连接（通常上限为 5 到 8 个），各自独立获取不同对象，获取后均断开。
过程：
先用 1 个连接获取 html，耗时 2 RTT；
解析出 5 个图像后，同时并发发起 5 个独立的 TCP 连接并行下载。
总耗时：2 + 2 = 4 RTT。

3. 持续非流水线连接（Persistent without Pipelining）
机制：服务器在发送响应后仍保持该 TCP 连接打开。客户端必须在收到前一个对象的响应后，才能在同一个连接上发出下一个对象的请求。
过程：
建立连接并获取 html，耗时 2 RTT；
连接不释放，依次发送第 1 到第 5 个图像的请求，每个图像在已有连接上花费 1 RTT。
总耗时：2 + 5 * 1 = 7 RTT。

4. 持续流水线连接（Persistent with Pipelining）
机制：保持 TCP 连接不释放，客户端在收到前一个响应之前，就可以一口气连续发出后续所有对象的请求。
过程：
建立连接并获取 html，耗时 2 RTT；
解析出 5 个图像后，在同一个连接中连续发出 5 个请求，服务器顺次流水线回传全部图像，仅需 1 个往返。
总耗时：2 + 1 = 3 RTT。

### 应用层模型解析

以发送 http 请求 + dns + ARP + 交换机自学习 + DHCP 为例。

#### DHCP 动态获取 IP

1. DHCP Discover（发现）：
   - 主机 A 在应用层生成 DHCP 请求，封装在 UDP 数据报中（源端口 68，目的端口 67）。
   - IP 层：源 IP 为 `0.0.0.0`，目的 IP 为受限广播地址 `255.255.255.255`。
   - MAC 层：源 MAC 为主机 A 的 MAC，目的 MAC 为广播 MAC `FF-FF-FF-FF-FF-FF`。
   - 交换机自学习：广播帧路过局域网交换机，交换机立刻把 `(主机 A 的 MAC, 入端口 1)` 记录到自己的 MAC 地址转发表（CAM 表）中！然后将此广播帧向除端口 1 外的所有端口泛洪（Flooding）。
2. DHCP Offer（提供）：
   - 局域网内的 DHCP 服务器（通常由默认网关路由器兼任）收到广播，分配一个未使用的 IP 给 A，通过单播或广播回送 Offer。
3. DHCP Request（请求） & DHCP ACK（确认）：
    - A 正式请求租用该 IP，DHCP 服务器回复确认报文。

- 最终成果：主机 A 彻底“合法落户”！此时主机 A 拥有了：
  - 本机私网 IP：`192.168.1.100`；
  - 子网掩码：`255.255.255.0`；
  - 默认网关路由器的 IP：`192.168.1.1`；
  - 本地 DNS 服务器的 IP：`211.1.1.1`；

#### ARP 解析网关 MAC

主机 A 准备在浏览器输入 `http://www.serverB.com`。
A 想要解析这个域名，必须先发报文给 DNS 服务器（`211.1.1.1`）。
A 用自己的子网掩码一算：`211.1.1.1` 和自己**不在同一个子网**！必须走**默认网关（`192.168.1.1`）**！
可是，A 的 ARP 缓存表是空的！A 根本不知道网关的 MAC 地址是多少，链路层无法打包！

1. A 发送 ARP 请求（广播）：
   - 内容：“谁是 `192.168.1.1`？请把你的 MAC 地址告诉我！”
   - 目的 MAC：`FF-FF-FF-FF-FF-FF`。
   - 交换机再次确认学习：确保主机 A 的端口映射最新，然后泛洪广播。
2. 默认网关单播回复 ARP 应答：
   - 网关收到广播，发现问的是自己，回复：“我是 `192.168.1.1`，我的 MAC 是 `MAC_Gateway`！”
   - 交换机自学习：网关的应答帧进入交换机，交换机立刻学习记录 `(网关的 MAC, 入端口 2)`！
   - 交换机查表发现目标是主机 A，精准单播转发给主机 A。

- 最终成果：主机 A 在本地 ARP 缓存表中写下：`192.168.1.1 -> MAC_Gateway`。

#### DNS 域名解析

现在 A 可以把数据包发给网关了，目标是去查出 `www.serverB.com` 的真正 IP！

1. 封装 DNS 查询报文：
   - 应用层：DNS 查询请求（查 `www.serverB.com`）。
   - 传输层：UDP 协议（目的端口 53）。
   - 网络层：源 IP `192.168.1.100`，目的 IP `211.1.1.1`（DNS 服务器 IP）。
   - 链路层：源 MAC `MAC_A`，**目的 MAC `MAC_Gateway`**！
2. 局域网转发与 NAT 转换：
   - 交换机查表，精准单播给网关。
   - 网关（NAT 路由器）收到报文，剥掉链路层，查看网络层：
     - 将源私网 IP 替换为网关公网 IP；
     - 将报文重新打包，通过广域网路由接口转发出去。
3. 公网迭代/递归查询：
   - DNS 服务器（或经过根、顶级域、权威域多轮迭代后）找到了 `www.serverB.com` 对应的公网 IP：`120.20.20.20`。
   - DNS 响应原路返回，网关根据 NAT 表反向转换，送回主机 A。

- 最终成果：主机 A 终于拿到了服务器 B 的 IP 地址：`120.20.20.20`！

#### TCP 三次握手

有了目标 IP，但在发送 HTTP 之前，传输层必须先建立一条端到端、可靠的虚电路连接！

1. 第一次握手（SYN）：
   - A 生成 `SYN=1, seq=x` 报文，目的端口 80，目的 IP `120.20.20.20`。
   - 经交换机、网关 NAT、公网各大自治域（OSPF、BGP 路由选择算法）跳跃转发，抵达服务器 B。
   - *（如果服务器 B 局域网也冷启动，B 的默认网关也会在内部广播一次 ARP 解析出 B 的 MAC，再送达 B 的网卡）*。
2. 第二次握手（SYN + ACK）：
   - 服务器 B 收到后，为该连接分配缓存和控制块，回送 `SYN=1, ACK=1, seq=y, ack=x+1`。
3. 第三次握手（ACK）：
   - 主机 A 收到 B 的回信，回复 `ACK=1, ack=y+1`。

- 最终成果：双方的 TCP 状态机均进入 `ESTABLISHED` 状态，连接通道正式开通！

#### HTTP 请求与响应

1. 发送 HTTP GET 请求：
   - 主机 A 在应用层组装 HTTP 请求报文：
     `GET /index.html HTTP/1.1\r\nHost: www.serverB.com\r\n...`
   - TCP 将其切片封装并打上序号发送。
2. 公网飞驰：
   - 报文穿过千山万水，穿透双向 NAT，安全送达服务器 B。
3. Web 服务器响应：
   - 服务器 B 的 Web 守护进程读取请求，返回 `HTTP/1.1 200 OK`，正文携带 HTML 网页数据。
4. 最终呈现：
   - 主机 A 收到响应报文，TCP 层向上交付给浏览器，浏览器内核解析渲染出漂漂亮亮的网页！

#### 应用层模型总结

| 阶段 | 核心协议 | 解决的根本痛点 | 涉及的关键硬件动作 |
| :--- | :--- | :--- | :--- |
| 0. 认祖归宗 | DHCP | A 没 IP、没掩码、没网关、没 DNS | 广播 Discover；**交换机记录 A 的 MAC** |
| 1. 摸清家门 | ARP | A 知道网关 IP，但链路层不知道网关 MAC | 广播求 MAC；**交换机记录网关的 MAC** |
| 2. 问询天下 | DNS | A 知道域名，不知道 B 的物理 IP | 跨公网 UDP 传输，NAT 替换 IP 与端口 |
| 3. 订立契约 | TCP | 准备发数据，但两端还没建立可靠连接 | 经过公网路由器跳步转发，三次握手置位 |
| 4. 互通有无 | HTTP | 真正的应用层数据请求与网页回传 | 建立在已通的 TCP 套接字之上流式交付 |
