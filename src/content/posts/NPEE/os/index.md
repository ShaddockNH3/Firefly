### 内核态与用户态

#### 库函数与系统调用

库函数一般是用户态的，但是系统调用是内核态的。

典型的例子有数学函数，例如 sin、cos 等。

即便是 malloc 也属于用户态，因为其本质是在堆区操作，而堆区是用户内存的一部分。

然而，库函数例如 scanf，需要进入内核态。但是，和 trap 指令类似的，它们也是在用户态进行的，只是委托操作系统完成。

#### 内核态

从虚拟存储系统的角度分析，假设一个 4GB 的地址空间，内核态可以访问全部的地址空间，而用户态只能访问 3GB 的地址空间。

例如内核态占据 3-4GB 的地址空间，用户态占据 0-3GB 的地址空间。虽然每个进程的虚拟地址都是独占的 4GB 地址空间，但是其中高地址的空间却是一样的，即从物理内核存储映射到了该逻辑地址。

内核态主要可以干 IO 操作，进程调度等，尤其需要注意：

open 和 read 操作都属于系统调用，属于内核态。

#### 中断与异常

其实这个概念来自于计组，异常又称内中断，中断又称外中断。

默认情况下，只说中断一般指的是外中断。

异常分为三种模式，陷阱、故障、终止。

陷阱也就是操作系统中最常用的，通过陷阱陷入内核态。

需要注意，是用户使用 trap 指令进入内核态。

这种情况下，处理完陷阱后，需要到下一条指令继续运行。

故障例如缺页、除以 0 等。

这种情况下，处理完故障后，需要回到当前指令重新运行。

终止是程序发生了严重错误，需要立即终止，不需要再执行后续的指令。

#### 分层

一层一层调用，速度慢，但是易于调试。

#### 模块化

某个模块需要调另一个模块的功能，一个模块出错可能会影响另一个模块。

#### 宏内核

效率高，但是较为复杂。

#### 微内核

效率较低（因为很多功能都需要打断当前进程跑去请求内核完成）

可扩展性好。

#### 外核

冷门考点，但也需要知道是什么。

具体来说，就是专门划分出来一硬件

### 虚拟机

#### 第一类虚拟机

硬件上的不同地址跑不同的操作系统，即硬件之上是第一类虚拟机管理程序，在这之上分别运行了不通的操作系统。

#### 第二类虚拟机

宿主机运行虚拟化软件，虚拟化软件上运行另一个操作系统。本质上全是用户态进程。

需要辨析，虚拟化软件的代码量肯定小于一个操作系统。误解的原因是将系统镜像理解为虚拟化软件代码的一部分。

## 进程

### 进程与线程

#### PCB 的辨析

PCB 是程序在创建的时候，由程序创建原语创建的。

其是一个进程存在的标志，并且 PCB 是进程存在的唯一标志。

PCB 里面存有父程序，队列，当前进程状态等。

比较重要的是页表始址（采用多级页表的时候是页目录表始址）

假设一个进程的物理地址是 16GB，逻辑地址是 4GB，并且分配高 1GB 给内核区。

那么每一个进程的高 1GB 都是内核区物理映射过来的，都是相同的。

#### 主存空间辨析

假设逻辑主存空间有 4GB，高 1GB 内存是内核态，低 3GB 内存是用户态。

那么对于一个进程，其逻辑地址可以理解为：

代码本体 - 全局变量 - 堆区 - 共享区 - 栈区 - 局部变量 - 内核区

其中，代码本题是地址最低的，堆区从低地址向高地址增长，而栈区从高地址向低地址增长。

#### 进程的三态

在进程调度的时候，即操作其 PCB，例如把 PCB 插入就绪队列。

就绪态，运行态，阻塞态。

```text

               ┌──────────────┐
               │    就绪态    │ <────────────────────────┐
               │ (Ready State)│                          │
               └──────────────┘                          │
                  │        ▲                             │
        获得CPU   │        │ 时间片用完                  │ 事件完成
       (进程调度) │        │ (超时中断)                  │ (I/O完成)
                  ▼        │                             │
               ┌──────────────┐         ┌──────────────┐ │
               │    运行态    │ ───────>│    阻塞态    │ ─┘
               │(Running State)│ 等待事件│(Blocked State)│
               └──────────────┘ (请求I/O)└──────────────┘

做这种题的时候，最重要的是注意辨析题目的要求是什么态转什么态。
```

#### 进程通信

- 共享存储：是下列最快的方式，因为直接访问即可

- 消息传递：分为间接模式和直接模式。直接模式是直接通信，间接模式是通过一片区域通信

- 管道模式：可以理解为生产者消费者问题的缓冲区，是半双工模式

- 信号传递：进程发送信号访问，大部分的信号用户可以自定义，但是少数不行，例如 kill。进程可以给自己发送信号，例如定时完成某任务

需要辨析管道和管程的区别，会把这俩近似的名词搞混。

#### 进程与线程的数据

不同进程之间不共享数据，所以对于不同进程的全局变量，不会引发竞争。

然而，由于线程没有独立的地址空间，是基于进程而生的，所以线程之间共享进程的数据，从而同一个进程的不同线程之间会引发竞争。

| 属性 | 进程 (Process) | 线程 (Thread) |
| :--- | :--- | :--- |
| **地位** | **资源分配的基本单位** | **CPU 调度的基本单位** |
| **设备分配** | **可以独立获得设备分配** | **不可以！只能共享进程的设备** |
| **拥有资源** | 拥有地址空间、文件、设备等 | 仅拥有极少量运行必需的寄存器和栈 |

#### 线程的三种方式

- 用户级线程：由应用程序的线程库在用户空间管理，操作系统内核完全感知不到。优点是线程切换极快（不需要切换到内核态）；缺点是一个线程阻塞会导致整个进程都阻塞，且无法直接利用多核 CPU。

- 内核级线程：由操作系统内核直接创建、调度和管理。优点是能真正利用多核并行执行，一个线程阻塞不会影响其他线程；缺点是线程的创建和切换开销比较大，需要频繁进出内核态。

- m 对 n 级线程：前两者的混合模式，将 m 个用户级线程映射到 n 个内核级线程（通常 m ≥ n）。优点是结合了前两者的长处，既保持了快速切换，又能发挥多核优势且避免全盘阻塞；缺点是系统的设计与调度实现极其复杂。

任何用户级进程都可以直接运行，不需要额外适配。

对于这类题需要注意的事情就是不要搞混用户级进程和内核级线程。

### 调度

#### 三类调度辨析

- 高级调度：即作业调度。从外存的后备队列中挑选作业调入内存并为其创建进程。发生频率最低。

- 中级调度：即内存调度。当内存不足时，将暂时不能运行的进程调到外存（挂起态）腾出内存空间；等内存充裕且条件满足时再调回内存。发生频率中等。

- 低级调度：即进程调度（CPU调度）。从就绪队列中选取一个进程，将 CPU 分配给它运行。发生频率最高（几十毫秒一次）。

#### 进程调度的时机以及优先级变化

具体题目具体分析，最重要的是搞清楚每一类任务导致从什么态变成什么态。

关于优先级变化，需要注意刚上处理机的进程不可以立刻降低优先级。考虑这样一种情况，采用的是优先级抢占式调度，如这么做，会导致一个进程刚上处理机就被撤下来。

#### 进程调度的方式与参数

抢占式调度与非抢占式调度。

注意一些概念：

- 周转时间：从提交到完成经历的总时间。公式：周转时间 = 作业完成时间 - 作业提交时间。

- 平均周转时间：多个作业周转时间的平均值。公式：平均周转时间 = (作业 1 的周转时间 + ... + 作业 n 的周转时间) / n。

- 带权周转时间：衡量作业相对等待程度的指标（比值恒 ≥ 1，越接近 1 越好）。公式：带权周转时间 = 作业周转时间 / 作业实际运行时间。

- 平均带权周转时间：多个作业带权周转时间的平均值。公式：平均带权周转时间 = (作业 1 的带权周转时间 + ... + 作业 n 的带权周转时间) / n。

做这种题一样需要注意辨析清楚题目里到底要我们干什么，求什么东西。

#### 上下文切换与模式切换

- 模式切换：CPU 在用户态与内核态之间的权限切换。当前运行的进程并没有改变，只需保存和恢复少量的硬件寄存器状态（如处理系统调用或硬件中断），开销较小。

- 上下文切换：CPU 控制权从一个进程转移到另一个进程。需要保存当前进程的完整 CPU 现场与虚拟内存映射，并加载新进程的状态，开销较大。

- 两者关系：上下文切换必然包含模式切换（调度必须在内核态执行）；但模式切换不一定会引发上下文切换（比如进程只是发了个简单的系统调用读取时间，处理完后仍回到该进程继续执行）。

#### CPU 调度方式

- 先来先服务（FCFS）：按作业到达的先后顺序进行调度，即按提交、到达的顺序。
- 短作业优先（SJF）：按作业的执行时间长短进行调度，即执行时间最短的作业优先。短作业优先可以是非抢占式的，也可以是抢占式的，默认是非抢占式的
- 高响应比优先（HRRN）：按作业的响应比高低进行调度，即响应比最高的作业优先。计算公式为 1 + 等待时间 / 估计运行时间。
- 优先级调度：按作业的优先级高低进行调度，即优先级最高的作业优先。优先级调度可以是非抢占式的，也可以是抢占式的。可以分为静态优先级和动态优先级。此外可以注意，系统一般大于用户，交互一般大于非交互，IO 一般大于计算，但是，这并不是绝对的
- 时间片轮转（RR）：一个绝对公平的算法，时间片选取需要取舍，因为切换进程也需要时间
- 多级队列调度：根据进程属性永久固定分配到不同优先级的队列中，进程不能在队列之间移动。
- 多级反馈队列调度：队列内的调度算法不一定是同一种算法。多个队列的优先级由高到低且时间片依次增大，未在规定时间片内完成的进程会被自动降入下一级队列，允许进程在不同队列间动态移动。

| 调度算法 | 是否可抢占 | 优点 | 缺点 | 适用于 |
| :--- | :--- | :--- | :--- | :--- |
| **先来先服务 (FCFS)** | 非抢占式 | 算法简单，实现成本低，绝对先来后到，无饥饿现象。 | 对长作业有利，对短作业极不友好，易产生护航效应（导致平均等待时间极长）。 | 批处理系统早期作业调度；不适合交互式系统。 |
| **短作业优先 (SJF)** | 默认非抢占式（抢占式版本为SRTF） | 理论上能够获得**最短的平均周转时间和平均带权周转时间**。 | 长作业可能长期得不到服务导致“饥饿”甚至饿死；作业运行时间全靠预估，难以准确掌握。 | 批处理系统（能够预估任务长度的场景）；不适用于交互式环境。 |
| **高响应比优先 (HRRN)** | 非抢占式 | 综合平衡了运行时间与等待时间；短作业优先调度，长作业等待久了响应比上升也能被服务，**避免了饥饿**。 | 每次进行调度前都必须重新计算等待队列中所有作业的响应比，系统开销较大。 | 批处理系统的作业调度。 |
| **优先级调度算法** | 可抢占 / 非抢占（两种模式均可） | 灵活性高，能紧随业务优先级调整，紧要任务（如中断、系统级）可被迅速响应；配合动态优先级可防止饥饿。 | 静态优先级可能导致低优先级作业永久饥饿；优先级反转与维护开销较高。 | 实时操作系统（抢占式）；通用分时操作系统（结合动态优先级）。 |
| **时间片轮转 (RR)** | 抢占式（时间片用完即被抢占） | 绝对公平，进程轮流获得CPU，响应速度快，绝不会发生饥饿。 | 频繁的上下文切换带来额外的系统开销；时间片过长退化为FCFS，时间片过短系统利用率极低。 | 分时操作系统；强交互式环境。 |
| **多级队列调度** | 视队列规则而定（通常高优先级队列可抢占低优先级） | 分类施策，能针对不同进程特性（如系统任务、交互任务、批处理）匹配最适宜的算法。 | 缺乏弹性，进程一旦入队不可迁移；高优先级任务过多时，低优先级队列极易陷入长久饥饿。 | 进程分类界限明确的通用系统。 |
| **多级反馈队列调度** | 抢占式（新进/高优先任务可抢占CPU） | 集百家之长，兼顾短作业的周转时间与交互任务的实时响应，**无需预先估算作业运行时间**。 | 逻辑复杂，实现难度高；若高优先级队列源源不断，最底层的长作业仍有饥饿风险。 | 现代通用分时操作系统（如 UNIX/Linux、Windows 等内核调度基石）。 |

#### 多处理机调度（偏冷的考点）

SMP 的调度面临两个核心矛盾：处理器亲和性和负载平衡。

当一个进程从一个 CPU 迁移到另一个 CPU 上时，应将第一个 CPU 的缓存设置为无效，然后重新填充第二个 CPU 的缓存。这种操作的代价较高，因此系统应尽量避免将进程从一个 CPU 移到另一个 CPU，而应尽量让一个进程运行在同一个 CPU 上，这称为处理器亲和性。

对于 SMP 系统，应尽量保证所有 CPU 的负载平衡（也称负载均衡），以便充分利用多处理机的优势。否则，一个或多个 CPU 会空闲，而其他 CPU 会处于高负载状态，且有一些进程处于等待状态。负载平衡应设法将负载平均分配到 SMP 系统的所有 CPU 上。

然而，负载平衡通常会抵消处理器亲和性带来的好处：保持一个进程运行在同一个 CPU 上的好处是可以利用它在该 CPU 的缓存，而将进程从一个 CPU 迁移到另一个 CPU 会失去这个好处。因此，在某些系统中，只有当不平衡达到一定程度后，才会触发进程迁移。

多处理机调度可以分为以下两种：

方案一：公共就绪队列

系统中仅设置一个公共就绪队列，所有 CPU 共享该队列。这种方案能很好地实现负载平衡，因为 CPU 一旦空闲，就会立刻从公共就绪队列中选择一个进程运行。缺点是各进程可能频繁地在不同的 CPU 上切换，处理器亲和性不好。

提升处理器亲和性的方法有两种：① 软亲和，指由调度程序尽量将一个进程保持在某个 CPU 上运行，但这个进程也可以迁移到其他 CPU 上。② 硬亲和，指由用户进程通过系统调用，主动请求系统将其绑定到固定的 CPU 上。例如，Linux 系统实现了软亲和，也支持硬亲和的系统调用。

方案二：私有就绪队列

系统为每个 CPU 设置一个私有就绪队列，当 CPU 空闲时，便从其对应的私有就绪队列中选择一个进程运行。这种方案很好地实现了处理器亲和性，缺点是必须进行负载平衡。

平衡负载的方法通常有两种：① 推迁移，指由一个特定的系统程序周期性地检查各 CPU 的负载，若发现不平衡，则从超载 CPU 的就绪队列中“推”出部分进程，迁移到空闲 CPU 的就绪队列，以实现负载平衡。② 拉迁移，指当某个 CPU 负载很低时，主动从超载 CPU 的就绪队列中“拉”取部分进程到自己的就绪队列。在实际系统中，推迁移和拉迁移常被结合使用。

### 同步与互斥

#### 临界资源与临界区

临界资源可以理解为操作系统中只能被一个进程访问的资源，例如打印机。

临界区则指的是 “代码”，临界区是访问临界资源的代码。

所以，对于每个进程而言，如果执行的是自己的代码，那么他们拥有自己的临界区。

#### 同步与互斥的辨析

假设 A 需要 B 提供的资源，那么就需要通过同步关系。

互斥可以理解为，当一个进程在访问临界资源时，其他进程不能访问该资源。

需要注意，不可以用同步和互斥简单的来判断信号初始量，而是要具体题目具体分析。

空闲让进：临界区空闲无进程时，允许一个请求进入的进程立即进入。

忙则等待：临界区已有进程在访问时，其他试图进入的进程必须等待。

有限等待：对请求访问的进程，应保证其在有限时间内能进入，防止饥饿死等。

让权等待：当进程暂时不能进入临界区时，应立即释放 CPU 资源（进入阻塞态），避免白白消耗 CPU 进行忙等。

#### 软件实现同步与互斥

单标法：

```c
// 进程 P0
while (turn != 0);       // 进入区：检查轮到谁
critical section;        // 临界区
turn = 1;                // 退出区：把权力转交给 P1
remainder section;       // 剩余区

// 进程 P1
while (turn != 1);       // 进入区：检查轮到谁
critical section;        // 临界区
turn = 0;                // 退出区：把权力转交给 P0
remainder section;       // 剩余区
```

- 解决了什么问题：
  实现了**基本的互斥访问**。由于全局只有一个 `turn` 变量指示权限，任何时刻最多只能有一个进程通过循环判定，保证了“忙则等待”。
- 发现了什么问题：
  **违背“空闲让进”准则**。该算法强制两进程**必须严格交替进入**。若 $P_0$ 退出后临界区已空闲，但 $P_1$ 短期内或永远不想进入临界区，则 `turn` 将永远保持为 1，$P_0$ 哪怕急需进入临界区也会被永远挡在外面，造成资源严重浪费。

双标志先检查法

```c
// 进程 P0
while (flag[1]);         // ① 进入区：先检查对方想不想进
flag[0] = true;          // ③ 进入区：自己表示想进
critical section;        // 临界区
flag[0] = false;         // 退出区：自己用完了
remainder section;       // 剩余区

// 进程 P1
while (flag[0]);         // ② 进入区：先检查对方想不想进
flag[1] = true;          // ④ 进入区：自己表示想进
critical section;        // 临界区
flag[1] = false;         // 退出区：自己用完了
remainder section;       // 剩余区
```

- 解决了什么问题：
  打破了算法一中“必须严格轮流交替”的束缚，允许同一个进程在临界区空闲时连续多次使用临界区。
- 发现了什么问题：
  **违背“忙则等待”准则**。核心缺陷在于**“检查”与“设置”操作不是原子的**。如果发生并发调度顺序 ① $\rightarrow$ ② $\rightarrow$ ③ $\rightarrow$ ④，两个进程都先发现对方为 `false`，随后各自将标志置为 `true` 并同时冲入临界区，导致互斥机制彻底崩溃。

双标志后检查法

```c
// 进程 P0
flag[0] = true;          // ① 进入区：先表达自己的意图
while (flag[1]);         // ③ 进入区：再检查对方想不想进
critical section;        // 临界区
flag[0] = false;         // 退出区：自己释放
remainder section;       // 剩余区

// 进程 P1
flag[1] = true;          // ② 进入区：先表达自己的意图
while (flag[0]);         // ④ 进入区：再检查对方想不想进
critical section;        // 临界区
flag[1] = false;         // 退出区：自己释放
remainder section;       // 剩余区
```

- 解决了什么问题：
  解决了算法二中“两进程同时闯入临界区”的问题。因为是“先举手示意、后查看对方”，确保了绝不会出现同时进入临界区的情况。
- 发现了什么问题：
  **违背“空闲让进”与“有限等待”准则（导致死锁/饥饿）**。若发生交错执行 ① $\rightarrow$ ② $\rightarrow$ ③ $\rightarrow$ ④，双方都先将自己的标志置为 `true`，随后都在 `while` 循环中检测到对方为 `true`，进而相互等待对方退出。此时临界区明明是空的，却没有进程进得去，导致两进程永久卡死在进入区。

Peterson 算法

```c
// 进程 P0
flag[0] = true;                    // 表达进临界区的意愿
turn = 1;                          // 主动谦让，优先允许对方进
while (flag[1] && turn == 1);      // 只有“对方想进 且 轮到对方”时才等待
critical section;                  // 临界区
flag[0] = false;                   // 退出区
remainder section;                 // 剩余区

// 进程 P1
flag[1] = true;                    // 表达进临界区的意愿
turn = 0;                          // 主动谦让，优先允许对方进
while (flag[0] && turn == 0);      // 只有“对方想进 且 轮到对方”时才等待
critical section;                  // 临界区
flag[1] = false;                   // 退出区
remainder section;                 // 剩余区
```

- 解决了什么问题：
  完美综合了算法一和算法三，同时满足了：
  1. 空闲让进：若对方不想进（`flag[j] == false`），自己可以直接进。
  2. 忙则等待：若双方同时请求，`turn` 的最终赋值必定有先后，后写入 `turn` 的进程会把优先权让给先写入的进程，确保同一时刻仅一人进入。
  3. 有限等待：彼此都有谦让机制，不会形成永久死锁与无限饥饿。
- 发现了什么问题：
  **违背“让权等待”准则**。未获得执行权限的进程依然在 `while` 循环中不断空转判断（即“忙等待”，Busy Waiting），白白霸占 CPU 时钟周期而没有主动进入阻塞挂起状态。

#### 硬件实现同步与互斥

中断屏蔽方法

```c
// 进程进入与退出临界区的典型模式
...
关中断;              // 进入区：禁止 CPU 响应中断，防止发生进程调度
临界区代码段;        // 临界区：保证独占执行
开中断;              // 退出区：恢复 CPU 响应中断的能力
剩余区代码段;        // 剩余区
...
```

- 解决了什么问题：
  从根源上杜绝了因“时钟中断”或“外部事件”导致的进程切换。由于单 CPU 下进程切换必须依赖中断，关中断后当前进程就能一口气将临界区执行完毕，**极为简单地保证了互斥执行（忙则等待）**。
- 发现了什么问题：
  1. **不适用于多处理器系统（SMP）**：关中断指令仅对当前执行指令的这颗 CPU 核心有效，其他 CPU 核心上的进程仍然可以正常并发执行并闯入同一临界区。
  2. **严重破坏并发与系统安全性**：若临界区较长，关中断会显著降低系统的并发能力和响应效率；关中断属于特权指令，若误开放给用户态程序，恶意进程一旦关中断后陷入死循环，整个操作系统将直接瘫痪崩溃。

TestAndSet 指令（TS 指令 / TSL 指令）

```c
// TS 指令的功能示意（硬件底层实现为原子操作，不可被中断）
boolean TestAndSet(boolean *lock) {
    boolean old;
    old = *lock;     // 1. 读取 lock 的旧值
    *lock = true;    // 2. 将 lock 强制置为 true（加锁）
    return old;      // 3. 返回旧值
}

// 进程实际调用的加锁逻辑
// lock 为全局共享变量，初值为 false（表示无锁）
while (TestAndSet(&lock));  // 进入区：原子测试并加锁，返回 true 则一直在此忙循环等待
critical section;           // 临界区
lock = false;               // 退出区：解锁，释放临界资源
remainder section;          // 剩余区
```

- 解决了什么问题：
  将软件算法中致命的“检查锁”与“设置锁”合二为一，由硬件电路直接打包成一条原子指令**。在进入临界区时绝不可能发生进程切换导致两个进程同时拿到锁；且由于 `lock` 是内存中的共享变量（配合硬件总线锁定），该机制**完全适用于多处理器系统**。
- 发现了什么问题：
  1. **违背“让权等待”准则**：未抢到锁的进程必须在 `while` 循环中死死空转（忙等待），极大地空耗 CPU 时钟周期。
  2. **可能导致“饥饿”现象（违背有限等待）**：当锁释放的一瞬间，所有正在自旋等待的 CPU/进程凭硬件总线抢占能力再次竞争，调度顺序完全随机，可能导致某些倒霉进程长期抢不到锁。

Swap 指令（XCHG 指令）

```c
// Swap 指令的功能示意（硬件底层实现为原子操作，不可被中断）
void Swap(boolean *a, boolean *b) {
    boolean temp = *a;
    *a = *b;
    *b = temp;
}

// 进程实际调用的加锁逻辑
// lock 为全局共享变量，初值为 false（表示无锁）
// key 为当前进程的私有局部变量
boolean key = true;         // 局部变量初始化为 true（代表手里拿着一把关着的锁）
while (key != false) {      // 进入区：只有通过交换拿到 false（开锁状态），循环才结束
    Swap(&lock, &key);      // 原子地交换 key 与 lock 的内容
}
critical section;           // 临界区
lock = false;               // 退出区：释放锁
remainder section;          // 剩余区
```

- 解决了什么问题：
  与 TS 指令本质相同，利用**硬件原子交换**，巧妙地用进程私有的 `key = true` 把共享的 `lock = false`“换”出来。一旦自己手里的 `key` 变成了 `false`，说明原先锁是开的，且此时共享的 `lock` 已经被自己置换成了 `true`（自动上了锁），**同样能跨多核 CPU 完美实现原子加锁与互斥访问**。
- 发现了什么问题：
  1. **违背“让权等待”准则**：只要 `key` 一直是 `true`，进程就会不眠不休地在 `while` 循环里不断执行 `Swap`，占用处理机资源造成忙等。
  2. **可能导致“饥饿”现象**：与 TS 指令相同，锁被放开的瞬间各个等待进程地位均等且随机争夺，无法从机制上严格保证每个等待进程都能在有限时间内获得临界区。

#### 互斥锁 / 自旋锁

```c
// 互斥锁的数据定义与操作（acquire 和 release 必须为原子操作）
boolean available = true; // 表示锁是否可用，初值为 true（开锁状态）
// 获取锁的操作
void acquire() {
    while (!available)
        ;                 // 进入区：若锁不可用则循环忙等待（自旋）
    available = false;    // 抢到锁，置为不可用
}
// 释放锁的操作
void release() {
    available = true;     // 退出区：释放锁，置为可用
}
// 进程典型使用流程
acquire();                // 申请锁
critical section;         // 临界区
release();                // 释放锁
remainder section;        // 剩余区
```

- 解决了什么问题：
  提供了一种最直观、最简单的互斥同步工具。将底层的硬件原子操作（如 TS/Swap 指令）封装为标准的 acquire() 和 release() 接口，保证在任意时刻临界区内最多只有一个进程在执行，满足了“空闲让进”与“忙则等待”。在多处理器（SMP）系统中，若临界区执行时间极短，等待的线程省去了进程上下文切换的巨大开销，效率极高。

- 发现了什么问题：
  1. 违背“让权等待”准则：未抢到锁的进程不会休眠，而是在 acquire() 中持续死循环（忙等待/自旋），白白空耗 CPU 周期。
  2. 单 CPU 系统下极度低效：若在单 CPU 系统中，占用锁的进程被切换下台，等待锁的进程只会占着 CPU 空转直到时间片耗尽，没有任何积极意义。

需要注意，互斥锁仍然违背让权等待原则，真正不违背让权等待原则的是信号量。

互斥锁只具有 0 和 1，表达不了丰富的信息。

此外，互斥锁是霸占 CPU 等待，而信号量是直接阻塞。

#### 信号量

P（signal）操作与 V（wait）操作。

注意整型信号量和记录型信号量的区别，前者违背让权等待，后者才是真正的全部遵守。

前者类似互斥锁的原理，后者职责是引入了等待队列的概念。

经典的 3 个模型放在大题解析那块。

#### 管程

深入理解一下管程。

管程可以勇宇进程的同步互斥，本质是代码，封装了变量和逻辑。

可以粗略地理解为一个大 key，key 内部锁着一些变量，例如读者写者问题中的 cnt。

考虑这样一种情况，对于读者写者问题，读者可以同时读，但是每一个读者也只能互斥的访问 cnt。

所以要辨析清楚，读者可以同时读，这个 “读” 指的是同时读文件，而不是同时读 cnt。

所以，管程内部只能有一个进程执行。

### 死锁

#### 资源竞争与推进顺序非法

#### 死锁与饥饿

饥饿指的是进程长时间无法获得所需资源，导致无法继续执行，然而在充分的时间里，还是可以获得资源的。

然而死锁指的是逻辑上已经不可以继续执行了。

#### 死锁的四个条件

- 互斥
- 不剥夺
- 请求并保持
- 循环等待

题目里很可能出这几个东西的辨析，尤其是关于不剥夺和请求并保持需要理解清楚。

不剥夺条件的意思是我申请到的资源不会被其他进程抢夺。

请求并保持的意思是我已经请求到了一个资源，我还需要另一个资源，我会在不释放我已经申请到的这个资源的前提下，申请另一个资源。

这俩要想清楚。

#### 死锁预防

死锁预防的方式是破坏四个条件。

- 破坏互斥条件：采用共享设备，然而很多设备都是独占的，所以很多时候并不可行。
- 破坏不剥夺条件：强行释放，一般不可取
- 破坏请求并保持条件：静态分配（一次性分配所有运行所需的）；动态释放（使用完的设备先释放）
- 破坏循环等待条件：设置资源有序分配法。

#### 死锁避免

典型的代表是银行家算法。

然而需要注意，其不是限制进程申请资源的顺序，而是在进程动态提出资源请求时，先进行安全性检测（试探性分配），若分配后系统仍能处于安全状态（即能找到安全序列）才予以分配，否则暂不分配让进程等待。

#### 死锁检测

注意要记得资源分配图。

可以采用以下三种方式来解除死锁：

- 资源剥夺
- 进程撤销
- 进程回退

一定要往经典模型去思考。

### 内存管理概念

#### 程序链接与装入

编译 - 链接 - 装入

| 链接方式 | 链接发生的时间节点 | 模块是否提前装入内存 | 核心优势 | 核心劣势 |
| :--- | :--- | :--- | :--- | :--- |
| 静态链接 | 程序**运行前**（编译成可执行文件时） | 全量打包，一次性装入 | 运行时无额外开销，直接执行 | 重复存储、浪费内存、升级困难 |
| 装入时动态链接 | 程序**装入内存时** | 全量装入（边装入边链接） | 便于模块独立更新与跨程序共享 | 未调用的模块也得跟着装入占用内存 |
| 运行时动态链接 | 程序**运行到需要时**（执行中动态按需） | **仅在调用时才装入** | 最大化节约内存，启动飞快 | 首次动态调用时有寻址和装入开销 |

辨析一下链接的三种方式：

静态链接是运行前就把需要的库打包好，占磁盘空间，然后装入时一次性全转入

装入时动态链接意思是边装入边链接，但也是全都装入

运行时动态链接意思是需要的模块才链接。

需要辨析链接和装入的区别。

| 对比维度 | 静态装入 (绝对装入) | 可重定位装入 (静态重定位) | 动态运行时装入 (动态重定位) |
| :--- | :--- | :--- | :--- |
| **地址转换时机** | **编译/链接时**（在程序产生时就已确定物理地址） | **装入内存时**（装入的一瞬间完成所有地址转换） | **程序执行时**（真正访问某条指令/数据时才实时转换） |
| **地址转换方式** | 无需转换。逻辑地址就是绝对物理地址。 | **软件重定位**。装入程序根据分配的起始地址，一次性修改程序内所有相对地址。 | **硬件重定位**。由 CPU 内置的**重定位寄存器（基址寄存器）**在取指执行时动态相加完成映射。 |
| **装入后能否移动** | **绝对不能**（地址全写死在二进制代码里） | **不能**（地址在装载时已固化，移动会导致内部引用错乱） | **可以自由移动**（只需修改重定位寄存器的基地址即可实现进程在内存中的换入换出和腾挪） |
| **硬件支持要求** | 仅需最简单的单一硬件，无特殊要求。 | 无需特殊硬件（纯软件算法修改地址）。 | **必须依赖专用硬件**（如 MMU、重定位寄存器、限长寄存器）。 |
| **内存分配要求** | 只能装入固定内存位置，仅支持单道程序。 | 必须分配连续的物理内存空间，一旦分配不可拆分。 | 允许分配连续空间，亦是后续**非连续分配、虚拟内存与分页分段机制的底层基石**。 |
| **适用场景** | 早期单道批处理系统、极简裸机嵌入式系统。 | 早期多道批处理系统（无虚拟内存概念）。 | **现代所有主流操作系统**（支持多任务并发、进程交换与虚拟内存）。 |

三种内存装入方式辨析

- 静态装入（绝对装入）：在编译或链接时就已经确定了绝对物理地址，指令中的地址直接写死，不需要任何重定位寄存器介入，仅适用于早期的单道程序环境。

- 可重定位装入（静态重定位）：装入程序在将模块载入内存时，根据分配的内存起始物理地址，通过纯软件方式一次性修改程序内的所有相对逻辑地址（加上起始基地址偏移量）。装入完成后物理地址就此固定，程序在运行期间**不可在内存中移动**。

- 动态运行时装入（动态重定位）：装入模块进入内存后依然保留相对逻辑地址，**将地址转换推迟到 CPU 实际执行指令的那一刻才动态进行**。在执行指令时，硬件（重定位寄存器）自动将逻辑地址与基地址相加得出物理地址，因此程序可以在内存中便捷地移动（支持紧凑以消除外部碎片）。

- 考点延伸辨析：在狭义的连续分配管理中（如**动态重定位分区分配**），每个进程仅依靠一个重定位寄存器，因此只能分配**连续的物理地址**，便于系统进行整体搬迁和碎片紧凑；而在更广义的现代内存管理中，“动态运行时装入”这一核心思想被直接拓展到了**基本分页、请求分页及分段等非连续（离散）分配机制**中（由单基址寄存器升级为页表基址寄存器+硬件MMU查表），从而彻底打破了物理地址必须连续的限制。

#### 内存保护、共享与回收

内存保护主要是通过重定位寄存器来判断，共享则是共享物理内存，将之映射到逻辑地址空间中。

分配和回收主要基于页式存储和段式存储管理。

此外，硬件资源是昂贵的，所以对于整个 CPU 可能只有一个重定位寄存器。

#### 连续分配策略辨析

- 单一连续分配

- 固定分区分配
  - 分区大小相等：其实还有应用，例如要管理 k 个相同的炼钢厂。
  - 分区大小不等

- 动态分区分配
  - 首次适应算法：每次匹配从头开始，找到第一个适配的空闲分区
  - 邻近适应算法：从上次分配结束的为止开始向后找到第一个可以适配的。
  - 最佳适应算法：每次都选择可以被容纳的最小的一块（需要注意重新排序），容易出现外碎片
  - 最坏适应算法：每次都选择最大的那一块（注意需要重新排序），大的装不进去

然而实际应用中，反而首次适应算法式最好的。

- 基于索引的算法
  - 快速适应算法：根据系统平时常用的，固定分几个不同大小的区，构成链表，然后找最小可以容纳的分配，缺点是实现复杂以及内碎片
  - 伙伴系统 (Buddy System)：所有可用空闲分区的大小均规定为 $2^k$（$k$ 为整数）。
    - 分配：为大小为 $S$ 的请求寻找能容纳它的最小 $2^i$ 分区；若当前无空闲 $2^i$ 块，则将更大的空闲块（如 $2^{i+1}$）对半切开分成两半（互为“伙伴”），重复折半直到切出合适的 $2^i$ 大小分配给进程。
    - 回收：当释放一块 $2^i$ 空间时，若其相邻的“伙伴块”也是空闲的，则立即合并为一个 $2^{i+1}$ 的大块，并可向上递归继续合并。**这个伙伴块是唯一固定的，例如我是原来大空间的右边一半，那么我一定是找左边那一半；反之亦然**
    - 评价：极大加快了查找与合并速度，有效减少了外部碎片，但会产生一定的内部碎片。
  - 哈希算法：以空闲区大小为关键字建立哈希表分配

#### 基本分页管理

- 基本分页管理的概念

  页面，页框，实页号，页号，物理页框等概念。

  以一个 4GB 的逻辑空间为例，如果页大小为 4KB，那么页号就是前 20 位，页内地址就是后 12 位。

- 基本地址变换

  如果越界中断，那么直接返回。如果没有越界，那么根据虚页号的前 20 位直接访问页表数组下标，得到物理页框号，物理页框号和原来的 12 位拼接，可以得到物理地址。

  需要注意，页表没有全相联、组相联之类的概念，硬要说的话，查页表时，像一维数组下标寻址，一对一直接索引（无需相联比较）；而物理块放置时，任意虚页可放入任意物理页框，本质映射策略是全相联。一定要区分页表和 TLB 的概念。

  页表类似数组 / 哈希表，而 TLB 才类似 cache（的组相联 / 全相联）！

- 基本分页的缺点

  页式管理容易产生内碎片。

#### 二级页表 & 多级页表

一级页表的问题是：页表必须是连续的，所以如果页表很大，那么会占用连续的主存空间。

考虑采用二级页表，即如果主存为 4GB，一级页表占 10 位，二级页表占 10 位，页面占 12 位，则根据原始逻辑地址的前 10 位映射找到对应二级页表的物理页号，然后根据物理页号直接找到对应二级页表的物理页。

然后根据中间 10 位得到逻辑地址的物理页号，然后再把这个物理页号和最后 12 位拼接得到真实的物理地址。

注意页表尽量都不要超过 1 页。

还是要辨析清楚，号和具体内存地址的关系。号 / 块一定指的是以 xx 为基准的。

在答题的时候，经常会**混淆以块为基准还是以具体地址为基准**！

事实上，对于一级页表（仅一级），页表始址寄存器也只用存其物理页号，而不需要存具体的 0 号记录对应的地址，因为边界对齐。

#### 段表

段式管理容易产生外碎片，不利于内存的利用；有利于程序的动态链接（因为是按逻辑的）；

段号，段长，段内偏移量。

注意，段表寄存器里存的是段表长度和段表初始地址！

段表的逻辑是先取出段号，如果段号 >= 段表长度，那么越界中断（段表越界）。和页表类似的，一个进程对应一个段表，而不是全局进程对应一个段表。

第二步如果段内盘偏移量 >= 段长，那么发成段内偏移中断。

一定要捋清楚地址对应的是什么，段表寄存器里存的是什么。

由于实际生活中分段已经几乎不使用了，所以考试也基本不大可能考大题。

段的长度不固定且段对用户不透明，程序员在指定的时候必须指定段号以及偏移量（是二维的）。

段可以共享，把物理段映射到不同的逻辑段。

#### 段页式

段页式即先分段再分页，本质是按页存储的。

在段页式存储中，每个进程仅有一张段表，但是可能有多个页表（每个段一张）

#### 页表的机制

#### 页框分配与置换

- 内存分配与置换策略

  这里的核心维度只有两个：

  - 分配策略：给一个进程的物理页框数是**固定死**的，还是**动态可变**的？
  - 置换策略：缺页要置换时，只能踢**自己进程**内部的页（局部），还是可以抢**其他进程**的页（全局）？

  三种合法组合：

  - 固定分配 + 局部置换：每个进程在运行前分配固定数量的物理块，运行期间总块数不变。发生缺页时，**只能在自己分到的那几个块里挑一个踢出去**。
  - 可变分配 + 全局置换：系统保留一个空闲物理块队列。进程缺页时，操作系统从空闲块队列里划拨一块给它；若空闲块用光了，系统可以**强行剥夺其他进程的物理块**分配给当前进程。
  - 可变分配 + 局部置换：根据进程缺页率的频繁程度，操作系统动态增加或减少分配给该进程的物理块数；但发生缺页置换时，**仍然只能从该进程自己的块里挑一个踢掉**。

- 为什么没有“固定分配 + 全局置换”？

  既然规定了“固定分配”，就要求每个进程拥有的物理块总数必须恒定不变。而“全局置换”允许从其他进程那里动态抢夺物理块，一旦抢了，被抢进程的块数减少，抢到进程的块数增加，两者的总块数都变了，直接打破了“固定”的前提！

- 调页时机

  - 预调页策略（Pre-paging）：
    - 何时发生：主要用于**进程启动前**（初始化时）。
    - 机制：利用空间局部性原理，预测进程接下来会用到哪些页，一次性把相邻的几个页提前调入内存。
    - 特点：靠预测，成功率只有 50% 左右，主要由程序员通过系统调用显式指定或用于大块数据批量加载。
  - 请求调页策略（Demand Paging）：
    - 何时发生：在**进程运行过程中**。
    - 机制：平时不调，只有当 CPU 访问该页发生**缺页中断（Page Fault）**时，才被动地从外存调入。
    - 特点：现代 OS 的通用标准策略，实现简单，但发生缺页时的 I/O 开销较大。

- 从何处调入页面？

  在外存（磁盘）中，空间被明确划分为两块：
  - 文件区：存放普通文件，追求离散存储以提高空间利用率，I/O 速度较慢。
  - 对换区（Swap 分区）：存放暂存的内存页面，采用**连续分配方式**，追求极致的 I/O 读写速度。

  页面调入的三种场景：

  - 对换区空间足够充足：
    - 进程运行前，把与该进程相关的所有数据从文件区**全部预先复制到对换区**。
    - 之后只要发生缺页，**一律直接从高速的对换区调入**；换出时也全部写回对换区。
  - 对换区空间不够充裕：
    - **没修改过的页（只读代码、未写过的数据）**：换出时直接丢弃，无需写入外存；下次需要时**直接去文件区重新读**。
    - **被修改过的页（脏页，Dirty Page）**：换出时必须**写入对换区**，下次缺页也**从对换区调入**。
  - UNIX 策略：
    - 与进程相关的代码段、数据段在第一次使用时，**统一从文件区调入**。
    - 只要这一页被调入过内存，一旦它未来被换出，**一律写入对换区**；下次如果再需要它，就改**从对换区调入**。
    - 和对换区空间不够的策略对比，对换区空间不够也是从文件去读入，不同点在于不充裕的时候，修改过的才放进对换区，而 UNIX 是只要访问过了就放对换区。

  “交换频繁而 CPU 很空闲”的现象，即**抖动（颠簸）**！

  本质原因：同时运行的**进程数量过多（多道程序度过高）**，导致分配给每个进程的物理块数量少于其**工作集（Working Set）**的大小。进程大部分时间都在等磁盘 I/O 调页，CPU 反而被闲置。

  解决抖动：

  1. 减少多道程序度：挂起或杀死部分进程，把腾出来的物理页框集中分给剩下的进程，确保每个进程都能装下其工作集。
  2. 增加物理内存容量：给服务器插更多的物理内存条。
  3. 基于工作集算法进行动态调整：防止给进程分配的页面数低于下限。

- 置换算法

  - OPT（最佳置换算法，Optimal）
    - 淘汰规则：淘汰**在未来最长时间内不再被访问**的页面。
    - 评价：性能最好，缺页率最低。但操作系统无法预知未来，因此**在物理上无法实现**，通常仅作为衡量其他算法优劣的理论上限。
  - FIFO（先进先出置换算法）
    - 淘汰规则：淘汰**最早进入内存**的页面。
    - 评价：实现最简单（维护一个队列），但性能很差，没有考虑局部性。
    - 致命考点——Belady 异常：正常算法物理块越多缺页越少，但 FIFO 会出现**为进程分配的物理块增加，缺页次数反而不减反增**的怪异现象！
  - LRU（最近最少使用算法，Least Recently Used）
    - 淘汰规则：淘汰**过去一段时间内最久未被访问**的页面。
    - 实现机制：依靠硬件计数器或双向链表/软件堆栈，记录每个页面的上次访问时间。
    - 评价：性能最接近 OPT，且属于**堆栈型算法**，**绝对不会产生 Belady 异常**！但硬件维护代价和开销极高。
  - CLOCK 算法（时钟置换 / NRU 最近未使用）
    - 淘汰规则：把内存中的页面排成一个**循环队列**，每页设置一个**访问位 $u$（0 或 1）**。
      - 当页面被访问时，硬件将 $u$ 置为 1。
      - 置换时，指针开始循环扫描：
      - 若遇到 $u = 0$，直接选定淘汰！
      - 若遇到 $u = 1$，将该位的 $u$ 清零（给一次免死机会），指针向前移动继续找。
      - 评价：以极小的硬件代价（仅需 1 个 bit）近似模拟了 LRU 的性能。
  - 改进型 CLOCK 算法（综合考虑【访问位 $u$】与【修改位 $m$】）
    - 核心思想：被修改过的页面（$m=1$）换出时需要写回磁盘，I/O 开销很大！所以**优先淘汰既没被访问、又没被修改过的页面**！
    - 扫描四步法（最多转 4 轮）：
      - 第 1 轮：找 $(u=0, m=0)$。不修改任何标志位，找到即淘汰。
      - 第 2 轮：若第 1 轮未找到，找 $(u=0, m=1)$。本轮经过的所有页面的**访问位 $u$ 必须全部清零**！找到即淘汰。
      - 第 3 轮：若仍未找到，重复第 1 轮，找 $(u=0, m=0)$。
      - 第 4 轮：若仍未找到，重复第 2 轮，找 $(u=0, m=1)$，此时必定能命中淘汰项。

### 目录与文件

#### FCB 与索引节点 inode

1. FCB 是操作系统中管理文件元信息的通用抽象结构，并非仅属于 FAT 系统；Unix 及 UFS 系统采用 FCB 分解法，将其拆分为目录项与 inode 两部分以减少目录检索时的磁盘读写次数。

2. 传统 FCB 中必须包含文件的物理地址以及权限等属性，文件的物理地址由 FCB 直接记录，但文件的具体数据内容存放在磁盘数据块中而非 FCB 中。

3. FAT 系统中的静态链表是 FAT 表即文件分配表，它位于磁盘卷的前端保留区，用于显式记录物理盘块的先后链接关系，其表项数量对应物理盘块数而非文件数。

4. FAT 系统中的 FCB 本质上就是目录项，它们并不集中在磁盘最前端，而是分散保存在各个目录文件的数据块中。

5. 在类 Unix 系统中，文件名不保存在 inode 中，而是与 inode 编号一同保存在目录项中；一个目录项就是文件名到 inode 编号的映射。

6. 文件的访问权限、文件主、文件大小以及用于寻址磁盘块的直接与间接物理索引指针，全部直接保存在 inode 内部，绝对不占用或保存在普通数据块中。

7. 类 Unix 系统在格式化时会预先在磁盘中分配固定数量的 inode 空间，因此磁盘中 inode 的最大数量确实决定了该文件系统能够创建的文件总数上限。

综上辨析一下 FCB 和 inode，只是说 FAT 系统使用了 FCB 方法，UFS 使用了 inode，并不是说 FCB 是 FAT 独占的。

#### 文件的基本操作

- 创建：在外存分配空间并建立 FCB/目录项，完成文件名到初始物理位置的绑定。
- 删除：释放文件占用的外存块，并在目录项中彻底抹去其记录。
- 读：根据读指针把外存/系统缓存里的数据搬运到进程的用户空间缓冲区。
- 写：把进程用户空间的数据写进外存/系统缓存，并更新文件指针与长度属性。

- 打开：把文件的 FCB 调入内存的打开文件表，并向进程返回一个数字代号（文件描述符）。
- 关闭：使文件打开引用计数减一，在进程打开表中注销该项，计数归零时清出系统表。

- 辨析 open 与 read：open 传入的参数是文件名，返回的是文件描述符；read 直接根据这个文件描述符去访问文件即可

- 辨析关闭和写入：关闭只是单纯的把文件（如果是最后一个关闭）从文件打开表删除，而在删除的过程中，文件并没有立刻写回磁盘，而是操作系统另外自行写回的。所以关闭和写回没有必然的强相关性。

- 辨析系统文件打开表和进程文件打开表：系统表全局仅一份、记录所有打开文件的物理信息与共享引用计数；进程表各进程独立持有一份、只记录本进程打开文件的描述符与指向系统表的偏移指针。

#### 硬链接与软链接

属于文件共享相关的。

- 硬链接：同一个 Inode 在不同目录项下的镜像别名，共享物理空间与链接计数，计数归零才真正释放数据。

- 软链接（符号链接）：一个独立的全新文件（拥有独立 Inode），内容仅为目标文件的路径字符串，目标失效即变“死链接”。

以文件 file.txt 为例，cnt = 1，假设硬链接出去，那么连接计数 cnt = 2，如果源文件软连接出去，那么新建一个 inode，该 inode cnt = 1。如果针对该 inode 再硬连接出去，那么该 inode cnt = 2。

删除源文件，那么源文件计数 cnt = 1，然后延伸出去的软连失效。

#### 文件系统空间管理

- 空闲表法：为所有连续的空闲区建立登记表，记录每个空闲分区的起始块号与长度，适合连续分配策略。
- 空闲链表法：
  - 空闲盘块法：把所有未分配的单个盘块通过指针串成一条总链，分配和回收逐块进行，适合离散分配但链条极长。
  - 空闲盘区法：把连续的空闲块作为一个盘区，盘区头记录长度并用链表串联各盘区，兼顾了分配速度与连续性。
- 位示图法：用连续的二进制比特位（0 与 1）直接映射整块磁盘每个盘块的占用与空闲状态，体积极小可常驻内存且便于快速计算块号。查找高效，但需要空间存储。
- 成组链接法：把空闲块按固定数量分组成栈并层层链挂，栈顶块记录下一组所有块号，兼具链表的扩展性与栈的批量高速存取性能（UNIX）。注意利用空闲盘块栈存储。

可以注意，文件系统空间这里指的是外存空闲区管理。

#### 虚拟文件系统

即 VFS。内核在内存中建立的面向对象的抽象接口层，用来屏蔽各类异构底层文件系统的物理差异，向上提供统一的系统调用。

- 超级块对象：代表一个已挂载的具体文件系统，负责记录该文件系统的全局控制信息与挂载元数据。
- V 结点对象：代表一个确切的物理文件本身，负责统管文件的访问权限、物理块映射及底层驱动函数指针（不存文件名）。
- 目录项对象：代表路径上的某一级目录或具体文件名，在内存中把字符串名字与对应的 V 结点绑定并构建路径缓存树。
- 文件对象：代表某个进程正打开的一个文件交互上下文，负责维护该进程当前独享的读写指针位置、访问模式及引用计数。

#### Spooling 技术

- Spooling 技术的基本部件

  输入井与输出井：开辟在外存（磁盘）上的两块专用大容量存储区。

  输入井：模拟脱机输入的磁带，暂存输入设备传来的海量作业数据。

  输出井：模拟脱机输出的磁带，暂存用户作业产生的海量输出数据。

  输入缓冲区与输出缓冲区：开辟在内存中的暂存区。负责在“内存”与“外存井”之间进行块级高速中转，抹平系统内部总线与磁盘的速度差。

  - 输入进程与输出进程（预设系统级软件）：
    - 输入进程：模拟脱机输入时的外围控制机，负责把输入数据打入输入井。
    - 输出进程：模拟脱机输出时的外围控制机，负责把输出井中的数据顺序拉取并喂给慢速物理外设。
  - 井管理程序：负责维护作业表项、排队状态及外存块指针。

- Spooling 技术的基本流程

  - 阶段一：逻辑申请（用户作业发起）

    - 用户进程向操作系统申请使用打印机；
    - 系统不分配真实打印机，而是由系统在内存中为该作业分配一个逻辑设备控制块，并在外存输出井中划定专用存储区域；
    - 用户进程通过系统调用，将待打印数据写入内存输出缓冲区。

  - 阶段二：井内暂存与用户释放

    - 缓冲区数据成块写入外存输出井；

    - 数据完全写入外存井后，操作系统直接给用户进程返回“I/O 已完成”信号；
    - 用户进程解除阻塞继续前行或正常终止退出，系统将该打印任务挂入“打印请求等待队列”。

  - 阶段三：后台守护调度（真正的物理输出）

    - 物理打印机空闲时，系统的 SPOOLing 输出进程 从打印队列中取出下一个就绪作业；
    - 输出进程从外存输出井将数据分批调入内存输出缓冲区；
    - 驱动物理打印机，将数据从缓冲区逐字/逐行发送至打印设备；
    - 打印彻底完毕后，输出进程释放该任务在外存井中所占用的所有物理磁盘块。

所以可以发现，用户在申请的时候是用户态，而真正后台守护调度使用的是内核态。

- 缓冲区也可以是内存，为什么 Spooling 技术需要外存支持

  考虑这样一种情况，假设打印的东西是 GB 级别的，那么内存会直接撑爆。

  内存缓冲区（Buffer）：主要用于匹配 CPU 与外设的速度差，生命周期短，容量极小（KB~MB 级），易失性，无法应对海量、长时间的数据积压。

  外存支持（井技术）：SPOOLing 面对的是极端慢速的机械/独占设备（如打印机），且多进程并发产生的数据量极其庞大（GB 级），数据滞留时间以“小时”甚至“天”计。

  容量瓶颈：若无外存的“输入/输出井”托底，海量输出数据将瞬间挤爆物理内存，导致系统发生内存耗尽（OOM）崩溃。

  驻留周期：慢速外设消费数据极慢，若长期霸占物理内存，会严重降低内存利用率与多道程序并发度。

  数据安全性：外存具备非易失性，可有效避免突发断电导致排队作业丢失。

#### 读者写者问题

主要是注意理解经典模型和非经典模型的差别。

- 经典模型：多读者一写者读优先

```c
semaphore rw_mutex = 1;  // 互斥访问共享数据区
semaphore mutex = 1;     // 互斥修改 read_count
int read_count = 0;

void reader() {
    while (1) {
        P(&mutex);
        read_count++;
        if (read_count == 1) {
            P(&rw_mutex); // 第一个读者锁住写者
        }
        V(&mutex);

        // --- 读操作 ---

        P(&mutex);
        read_count--;
        if (read_count == 0) {
            V(&rw_mutex); // 最后一个读者释放写者
        }
        V(&mutex);
    }
}

void writer() {
    while (1) {
        P(&rw_mutex);
        // --- 写操作 ---
        V(&rw_mutex);
    }
}
```

```c
int read_count = 0;

void reader() {
    while (1) {
        P(&write_gate);  // 检查是否有写者插队封锁
        P(&mutex);
        read_count++;
        if (read_count == 1) {
            P(&rw_mutex); // 封锁写操作
        }
        V(&mutex);
        V(&write_gate);

        // --- 读操作 ---

        P(&mutex);
        read_count--;
        if (read_count == 0) {
            V(&rw_mutex);
        }
        V(&mutex);
    }
}

void writer() {
    while (1) {
        P(&write_gate);  // 抢先占住门禁，阻止新的读者进来
        P(&rw_mutex);    // 等待正在读的读者全部退出
        
        // --- 写操作 ---

        V(&rw_mutex);
        V(&write_gate);  // 释放门禁
    }
}
```

### 二级分页 + TLB 模型

系统参数设定

- 逻辑地址空间：4GB，按字节编址，逻辑地址长度为 32 位。
- 页面大小：4KB。
- 二级分页划分：高 10 位为一级页号（页目录号 P1），中间 10 位为二级页号（P2），低 12 位为页内偏移量（D）。
- TLB：全相联映射，初始状态全空。
- 访存策略：CPU 给出虚地址后，先查 TLB。TLB 缺失时，才去查内存中的页表。若发生缺页，由操作系统调入页面并更新页表，中断返回后重新执行该指令。

某时刻，CPU 执行一条访存指令（比如 LOAD 寄存器, [0x0040312C]），尝试读取该逻辑地址处的数据。

此时：

1. 目标页面在外存（磁盘 Swap 区），尚未调入主存。
2. TLB 处于清空状态。
3. 页目录表已在物理内存中，其基地址寄存器指明了页目录的物理地址。

#### 阶段一：第一次执行指令与虚地址切分

1. CPU 解析逻辑地址 0x0040312C，将其转换为 32 位二进制：
   0000 0000 0100 0000 0011 0001 0010 1100
2. 硬件自动将其拆解为三部分：
   - 一级页号 P1（前 10 位）：0000 0000 01，即十进制 1 号目录项。
   - 二级页号 P2（中 10 位）：00 0000 0011，即十进制 3 号页表项。
   - 页内偏移 D（后 12 位）：0001 0010 1100，即十六进制 0x12C。
3. 虚页号 VPN 为前 20 位组合：0000 0000 0100 0000 0011，即十六进制 0x00403。

#### 阶段二：查询 TLB（发生 Miss）

1. CPU 硬件拿着 20 位虚页号 0x00403 去和 TLB 中所有条目的 Tag 进行全相联并行匹配。
2. 判定：由于 TLB 初始为空，Tag 匹配失败（TLB Miss）。
3. 动作：按照设定，硬件转向内存开始查询二级页表。

#### 阶段三：两级页表漫游与触发缺页

1. 查一级页目录表：
   - 硬件根据页表基址寄存器 + (P1 × 4B)，找到 1 号页目录项。
   - 检查该项有效位为 1，从中读出对应的二级页表所在的物理页框号。
2. 查二级页表：
   - 硬件根据二级页表基地址 + (P2 × 4B)，找到 3 号页表项。
   - 检查该页表项：发现其有效位（Valid Bit）为 0！说明该目标数据页不在内存中。
3. 触发异常：
   - 硬件立即终止当前地址变换，产生【缺页异常（Page Fault）】，CPU 进入核心态。

#### 阶段四：操作系统介入（缺页中断服务程序）

1. 操作系统挂起当前触发缺页的进程，保存当前指令的上下文（PC 依然指向这条引发缺页的 LOAD 指令）。
2. 从空闲物理页框列表中分配一个空闲页框（假设分配到的物理页框号为 0x5A88）。
3. 根据页表项中记录的外存地址，发出磁盘 I/O 请求，把外存中的数据页面读入到 0x5A88 页框中。
4. 页面调入完成后，操作系统修改该二级页表项的内容：
   - 将物理页框号写入 0x5A88。
   - 将有效位从 0 改为 1。
5. 中断处理结束，CPU 退出核心态。

#### 阶段五：异常返回与“重读重执”

1. 重点特性：与普通的外部 I/O 中断不同，缺页异常处理完成后，CPU 恢复现场，返回到【刚刚发生缺页的那条原指令】重新开始执行，而不是执行下一条指令。
2. CPU 再次发射这条 LOAD [0x0040312C] 指令。

#### 阶段六：第二次执行指令与 TLB 更新

1. CPU 再次切分地址，得到虚页号 0x00403。
2. 先查 TLB：**因为操作系统刚刚调页并不会直接主动写 TLB，此时 TLB 里仍然没有这个项，再次发生 TLB Miss。**
3. 再次查两级页表：
   - 查页目录项（有效）。
   - 查二级页表项：这次读取时，有效位已经是 1 了！顺利读出物理页框号 0x5A88。
4. 写入快表：硬件（或软故障处理）将映射关系【Tag = 0x00403, 物理页框号 = 0x5A88】写入全相联 TLB 中，以便下次极速访问。

#### 阶段七：最终物理地址拼接与访存

1. 物理地址生成：
   - 高位取物理页框号：0x5A88（二进制占对应物理位宽）。
   - 低 12 位直接复制逻辑地址的页内偏移：0x12C。
   - 最终物理地址合成完毕：0x5A8812C。
2. CPU 将该物理地址送上地址总线，从主存中正确读出数据，装入寄存器，整条指令顺利执行完毕！

### 连续分配、隐式链接添加和删除文件需要访问多少次磁盘

假设对于一个长度为 100 磁盘的文件，现在需要向第 29 块后插入第 30 块。

- 连续分配
  - 先读出前 29 块，然后向前移动一个（写入 29 次），最后写入第 30 块（29×2+1）。前提是前后都有空间，否则就是读后 70 块向后移动一个，写入第 30 块（70×2+1）
- 隐式链接
  - 读入前 29 块（得到原来第 30 块的地址），写入新第 30 块，修改第 29 块的末尾只恨（29+1+1）

对于显示链接分配和索引分配，直接参考 FAT 系统和 UFS 系统即可。

### FAT 系统与 UFS 系统

假设根目录内容已经被读入了（即 A 的 FCB / inode 已经在内存里了）。

要读取文件 C 的第 1048 块

#### 以 FAT 系统为例，访问 ./A/B/C

在 FAT 系统中，FAT 表开机即载入并常驻内存，目录也是文件，FCB 即目录项。

- open 阶段：获取 C 的元数据，在内存中登记并返回文件描述符 fd
  - 读取 A：根据块号，读磁盘将目录文件 A 的盘块读入内存。在 A 中遍历查找目录项 B，获得 B 的起始物理块号。
  - 读取 B：根据块号，读磁盘将目录文件 B 的盘块读入内存。在 B 中遍历查找目录项 C
- read 阶段：从 C 的 FCB 中拿到起始块号。因为 FAT 表完全在内存中，系统在内存的 FAT 表中顺着指针链条追踪（做 1047 次链表跳转），即可在内存中瞬间计算出第 1048 块的真实物理块号。根据算出的物理块号，读磁盘 1 次，将第 1048 块的数据内容送入用户缓冲区。

open 访问磁盘：2 次。

read 访问磁盘：1次。

#### 以 UFS 系统为例，访问 ./A/B/C

- open 阶段
  - 读 A 的 inode：根据 inode 编号去磁盘的 inode 区读出 A 的 inode。
  - 读 A 的目录项：根据 A 的 inode 里的直接指针，读出 A 的目录数据块。在其中匹配得到 B 的 inode 编号。
  - 读 B 的 inode：根据 B 的 inode 编号去磁盘的 inode 区读出 B 的 inode。
  - 读 B 的目录项：根据 B 的 inode 里的直接指针，读出 B 的目录数据块。在其中匹配得到 C 的 inode 编号。
  - 读 C 的 inode：根据 C 的 inode 编号去磁盘的 inode 区读出 C 的 inode。
- read 阶段
  - 此时 C 的 inode 已经在内存中。我们需要判断第 1048 块（逻辑块号 1047，若按 1-based 算则是第 1048 块）落在哪里：
    - 直接索引：第 $0 \sim 11$ 块（共 12 块）。
    - 一级间接索引：第 $12 \sim 12 + 1024 - 1 = 1035$ 块（共 1024 块）。
    - 二级间接索引：第 $1036 \sim 1036 + 1024 \times 1024 - 1$ 块。
    - 因此，第 1048 块必定落在二级（双重）间接索引中
  - 读入第一层索引块
  - 读入第二层索引块
  - 读入数据

open：5 次。
read：至少 1 次，按照本题设置的情景为 3 次。

### 以 scanf 分析设备管理

当程序执行到 `scanf` 时，库函数先检查 `stdio` 缓冲区；只有缓冲区中没有满足格式要求的数据时，才会通过 `read` 等系统调用进入内核。若输入尚未就绪，该系统调用会使进程阻塞。

键盘输入通常由设备中断交给驱动和终端行规程处理，再进入内核缓冲区。当缓冲区中已有满足本次读取的数据时，内核将数据复制到用户缓冲区并唤醒等待进程；具体的缓冲、回显、行结束和调度时机取决于操作系统与终端配置。

系统调用返回后，`scanf` 在用户态缓冲区中解析数据并返回。

简单来讲，就是执行 scanf 后，如果没有数据，那么使进程阻塞，等待用户输入数据。当用户输入数据的时候，数据首先进入键盘缓冲区，然后中断服务条例结束。

随后数据进入内核缓冲区，复制到用户缓冲区，然后使进程变为就绪态，等待进程唤醒。

进程被唤醒后，完成该函数，然后进入下一条函数（所以函数返回是最后做的）。
